# Design

## Context

Зачем — см. proposal.md. Что должно работать — см. specs/birthdays/spec.md и specs/data-ownership/spec.md.

Что есть сейчас:

- Контакты — таблица `contacts` (`src/db/schema.ts`), все запросы — в `src/db/contacts.ts`, каждый с `userId` первым аргументом. Сохранение — `createContact` / `updateContact` из `ContactInput`.
- Форму разбирает `parseContactForm` (`src/lib/contact-form.ts`) — чистая функция, покрыта Vitest. Форма одна для нового и существующего контакта (`src/components/contact-form.tsx`), поля в сетке из двух колонок. У `select` есть обход: `key={value}`, иначе после сохранения он сбрасывается (Next 16, React Activity).
- Блок «Пора связаться»: запрос `listDueContacts` считает дни в SQL по московскому времени (`APP_TIME_ZONE`) и отдаёт `today` строкой `YYYY-MM-DD`; серверный компонент `DueContacts` готовит подписи, клиентский `DueContactsList` рисует. Главная `src/app/(app)/page.tsx` не запрашивает блок во время поиска и при выбранной группе.
- Подписи дат и чисел — в `src/lib/keep-in-touch.ts`: `formatDay`, `formatDayCount` через `Intl.PluralRules`. Даты из базы — строки `YYYY-MM-DD`, форматируются как UTC, чтобы день не сдвигался.
- Тесты: Vitest (чистые функции и запросы к тестовой базе `*_test`), e2e Playwright на настоящей базе; e2e не меняет «сегодня», а подстраивает данные под `now()` базы (`e2e/keep-in-touch.spec.ts`). Хелперы дат `src/test/days.ts`.

## Goals / Non-Goals

**Goals:**

- Дата без года хранится честно, без выдуманного года-заглушки.
- Все пограничные случаи блока — переход через Новый год, 29 февраля, «сегодня» и «через 7 дней» — проверяются Vitest на фиксированных датах, без подмены часов базы.
- Неверная дата не попадает в базу ни через форму, ни подделанным запросом.

**Non-Goals:**

- Индекс по дате рождения: контактов у одного пользователя сотни, не миллионы.
- Тесты React-компонентов: вёрстку и поведение в браузере закрывает Playwright.

## Decisions

### 1. Три столбца `smallint`: `birth_day`, `birth_month`, `birth_year`

Все три — `NULL`, если не указано. Ограничения в базе (`CHECK`):

- день и месяц либо оба есть, либо оба `NULL`; год без дня и месяца невозможен;
- `birth_month` от 1 до 12, `birth_day` от 1 до 31, `birth_year` от 1900.

Какой день есть в каком месяце и «дата не в будущем» проверяет код (решение 3): `CHECK` с «текущим годом» в Postgres ненадёжен — `now()` в ограничении не пересчитывается для уже сохранённых строк.

Почему не столбец `date`: у `date` год обязателен. Пришлось бы хранить год-заглушку (например, 0004 — високосный, чтобы влезло 29 февраля) и отдельный флаг «год неизвестен». Любой запрос, забывший про флаг, покажет возраст 2022 года. Три поля проще прочитать и труднее использовать неправильно.

Почему не строка `MM-DD` + год: ограничения и сравнение строк хуже, чем чисел, а выигрыша нет.

Миграция только добавляет три пустых столбца и ограничения — существующие строки им удовлетворяют, данные не меняются.

### 2. Поле в форме: два списка и поле года

- «День» — `select`: пусто, 1–31. «Месяц» — `select`: пусто, «января» … «декабря» (родительный падеж: читается как дата «14 ноября»). «Год» — `input` с `inputMode="numeric"`, необязательный, `placeholder="Год"`.
- Три элемента в одной строке под общей подписью «Дата рождения» (`fieldset` + `legend`, у каждого элемента свой `aria-label`). Ошибка — одна, под строкой, связана через `aria-describedby`.
- Место в сетке — после «Как часто общаться»: седьмая ячейка, на телефоне — одна колонка, как остальные поля.
- Списки получают `key` по значению — тот же обход, что у частоты.

Почему не `<input type="date">`: он требует год, а у нас год по желанию; и календарь, начинающийся с текущего года, неудобен для даты рождения.

Почему день — список, а не поле: нельзя ввести «abc», и на телефоне выбор из списка удобнее.

### 3. Разбор и проверка — в `src/lib/birthdays.ts`, вызывается из `parseContactForm`

`parseBirthDate({ day, month, year }, today)` → `{ ok, value: { day, month, year } | null }` или ошибка. Правила по порядку:

1. Все три пустые → даты нет (`null`).
2. День или месяц пуст → «Укажите день и месяц».
3. День не целое 1–31 или месяц не целое 1–12 (только подделанный запрос) → «Такой даты нет».
4. Год есть, но не четыре цифры или вне 1900…текущий год → «Укажите год от 1900 до ‹текущий год›».
5. Такого числа в месяце нет: с годом — по этому году, без года — по високосному (29 февраля можно) → «Такой даты нет».
6. С годом и дата позже сегодняшней → «Эта дата ещё не наступила».

`parseContactForm(formData, today)` получает `today` строкой `YYYY-MM-DD` по московскому времени; действия берут её из новой `todayInAppTimeZone()` (`Intl.DateTimeFormat` с `APP_TIME_ZONE`). Так функция остаётся чистой и тестируется на любой дате. Ошибка ложится в `errors.birthDate`, введённые значения — в `values.birthDay / birthMonth / birthYear`.

### 4. Ближайший день рождения считает код, не SQL

- Запрос `listBirthdayContacts(userId)` отдаёт контакты пользователя с указанной датой: `id`, `name`, `birthDay`, `birthMonth`, `birthYear`, плюс `today` из базы по `APP_TIME_ZONE` — тот же источник «сегодня», что у «Пора связаться».
- Чистая функция `upcomingBirthdays(rows, today)` в `src/lib/birthdays.ts`: для каждого — день рождения в этом году (29 февраля → 28 в невисокосный), если он уже прошёл — в следующем; `daysUntil` от 0 до 7 оставляет, сортирует по `daysUntil`, затем по имени (`Intl.Collator("ru-RU")`), затем по `id`. Возраст — год праздника минус год рождения, если год известен.

Почему не SQL, как у «Пора связаться»: там правило — «день + интервал», Postgres делает его сам. Здесь нужна своя логика года праздника и 29 февраля, и её важно проверить на 28 декабря, 25 февраля 2027 и 2028 — в SQL это возможно только подменой `now()`. В коде это обычные тесты Vitest. Цена — в приложение приходят все контакты с датой рождения (сотни строк из двух чисел и имени) — пренебрежимо.

### 5. Подписи

В `src/lib/birthdays.ts`:

- `formatBirthdayBadge(daysUntil)` → «Сегодня», «Завтра», «Через N дней» (через `formatDayCount`).
- `formatTurningAge(age, isToday)` → «исполнится 35 лет» / «исполняется 21 год»: `Intl.PluralRules` с формами «год / года / лет».
- Дата в строке — `formatDay` из `keep-in-touch.ts` без года (год праздника всегда этот или следующий, «2 января» понятно и так). Чтобы не тащить лишнее, `formatDay` и `formatDayCount` остаются где есть и импортируются.
- `BIRTH_MONTHS` — названия месяцев для списка.

### 6. Блок на главной

- Серверный компонент `BirthdayContacts` (`src/components/birthday-contacts.tsx`): получает строки, готовит подписи, рисует карточку `section` с заголовком `h2` «Скоро день рождения» и списком. Без пустого состояния: строк нет — ничего не рисует. Клиентский код не нужен: ни галочек, ни сворачивания.
- Строка — по образцу строки «Пора связаться»: аватар-инициалы не нужны, имя — ссылка, растянутая на всю строку (`after:absolute`), дата, пометка-«чип» (сегодня — выделенная, остальные — спокойные, цвета из токенов), возраст, шеврон.
- Главная: `listBirthdayContacts` запрашивается в том же `Promise.all`, при поиске или выбранной группе — не запрашивается; блок ставится перед `DueContacts`.

### 7. Тестовые данные

`src/db/seed.ts`: примерно у трети контактов дата рождения, у четверти из них без года, у 2–3 — день рождения сегодня и в ближайшие дни (считая от дня запуска seed). Порядок вызовов `faker` для уже существующих полей не меняется: новые значения генерируются после, чтобы прочие данные seed остались прежними.

### 8. Тесты

- Vitest `src/lib/birthdays.test.ts`: `parseBirthDate` (все ошибки и граничные даты), `upcomingBirthdays` (сегодня, +7, +8, вчера, Новый год, 29 февраля в 2027 и 2028, порядок), подписи и склонения.
- Vitest `src/lib/contact-form.test.ts`: поле даты в `parseContactForm`, значения сохраняются при ошибке.
- Vitest `src/db/contacts.test.ts`: дата сохраняется, убирается, без года; `listBirthdayContacts` отдаёт только своё и только с датой; `CHECK` отклоняет день без месяца.
- Playwright `e2e/birthdays.spec.ts`: дату указали — сохранилась после обновления; ошибка «Такой даты нет»; блок с контактами «сегодня», «завтра», «через 7 дней», без «через 8», порядок, над «Пора связаться», скрыт при поиске и группе, переход в карточку. Даты в данных считаются от «сегодня» базы, как в `keep-in-touch.spec.ts`.
- `e2e/two-users.spec.ts`: блок «Скоро день рождения» у второго пользователя не показывает чужой контакт.

## Risks / Trade-offs

- [«Сегодня» для проверки формы берётся из часов приложения, для блока — из часов базы] → Обе стороны считают по `Europe/Moscow`; часы контейнеров синхронизированы с сервером. Расхождение возможно лишь в доли секунды у полуночи и влияет только на «дата в будущем» для родившихся сегодня.
- [В приложение приходят все контакты с датой рождения] → Сотни коротких строк; если контактов станет на порядки больше, фильтр по месяцам можно перенести в SQL, не меняя спеку.
- [Блок без сворачивания станет длинным] → За 8 дней дней рождения обычно немного; при 1000 контактов в среднем около 20. Если станет мешать — сворачивание как у «Пора связаться», отдельной правкой.
- [Шаблон формы растёт] → Поле — отдельный компонент `BirthDateField`, `contact-form.tsx` только вставляет его.

## Migration Plan

1. Миграция Drizzle: `ALTER TABLE contacts ADD COLUMN` × 3 и `CHECK`-ограничения. Данные не меняются, показывать миграцию отдельно до merge не требуется (правило CLAUDE.md — только для миграций, меняющих данные), но она будет в PR.
2. Выкатка обычная: тест-стенд → прод вручную; миграция — разовым контейнером до старта нового образа.
3. Откат: прошлая версия приложения через Deploy prod с галочкой «откат». Новые столбцы старой версии не мешают — она их не читает, восстанавливать базу не нужно. Даты рождения, введённые после выкатки, при этом остаются в базе и снова видны после повторной выкатки.
