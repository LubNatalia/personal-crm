# Design

## Context

Зачем - см. proposal.md. Требования - `specs/user-auth`, `specs/data-ownership` и дельты `contact-groups`, `contact-deletion`.

Что есть сейчас:

- Входа нет. Все страницы (`src/app/page.tsx`, `contacts/[id]`, `contacts/new`, `groups`) и server actions (`src/app/actions.ts`) работают со всеми данными базы.
- Слой данных - `src/db/contacts.ts`, `src/db/groups.ts`: функции принимают только номер записи. Таблицы `contacts`, `groups`, `contact_groups` без владельца; уникальность группы - индекс `groups_name_lower_idx` на `lower(name)` по всей таблице.
- База создаётся лениво (`getDb()`), потому что `next build` идёт без `DATABASE_URL`.
- Миграции - `src/db/migrate.ts` в разовом контейнере из образа приложения; Drizzle применяет их одной транзакцией на одном соединении. Демо-данные - `src/db/seed.ts`. Оба файла копируются в образ в `/db` и запускаются Node без сборки: импортировать могут только `drizzle-orm`, `postgres`, `@faker-js/faker`, `@next/env` и соседние файлы.
- Тесты: Vitest на отдельной базе `*_test`, Playwright на `*_e2e_test` против production-сборки на порту 3200. CI - Postgres как service container.
- Репозиторий публичный: личные данные (почта владельца) в код не попадают.
- Next.js 16: вместо `middleware.ts` - `proxy.ts`.

## Goals / Non-Goals

**Goals:**

- Одно место правил входа: и форма, и прямой запрос к серверу проходят одинаковые проверки почты и лимита.
- Владелец проверяется в каждом запросе к базе, а не только в интерфейсе: чужой номер записи ведёт себя как несуществующий.
- Одна сборка образа для локальной работы, автотестов и сервера; различие - только в настройках.
- Миграция не теряет записей и не стартует новую версию, если владелец данных не задан.

**Non-Goals:**

- Всё из раздела «Не делать» спеки: пароли, соцсети, код из письма, профиль, смена почты, удаление аккаунта, общий доступ, роли.
- Список устройств и «выйти везде».
- Защита от сканеров ссылок в почтовых программах (страница подтверждения перед входом) - см. Risks.
- Ограничение на уровне базы, что контакт и группа в связи принадлежат одному владельцу (проверяется в коде и тестами).

## Decisions

### 1. Better Auth + плагин magic link + Drizzle adapter

Вход - Better Auth (задан в CLAUDE.md) с плагином `magicLink`, адаптер Drizzle для Postgres. Таблицы Better Auth (`user`, `session`, `account`, `verification`) описываются в схеме Drizzle (сгенерировать CLI Better Auth, положить рядом со `schema.ts`) и попадают в обычную миграцию drizzle-kit. Обработчик Better Auth - `src/app/api/auth/[...all]/route.ts`. Плагин `nextCookies()` - последним, чтобы server actions могли ставить и снимать cookie входа.

Экземпляр создаётся лениво (`getAuth()`), как `getDb()`: иначе `next build` упадёт без `DATABASE_URL` и секрета.

Настройки Better Auth:

- `magicLink.expiresIn` = 15 минут; `disableSignUp` выключен - первый вход создаёт пользователя.
- `session.expiresIn` = 30 дней, `session.updateAge` = 1 день: каждый заход (не чаще раза в сутки) сдвигает конец входа на 30 дней вперёд. Кэш сессии в cookie выключен, чтобы «Выйти» действовал сразу.
- Сессии на разных устройствах независимы (поведение Better Auth по умолчанию); выход удаляет только текущую.

Альтернатива - свой вход на токенах в таблице: меньше зависимостей, но больше своего кода безопасности; Better Auth задан в стеке.

### 2. Правила почты и лимит - в Better Auth, форма их только переводит в текст

Почта приводится к виду `trim().toLowerCase()` и проверяется одной функцией `parseLoginEmail` (`src/lib/login-email.ts`, без зависимостей, покрыта тестами).

- `hooks.before` Better Auth на пути `/sign-in/magic-link`: нормализует почту и проверяет её `parseLoginEmail`; неверная - ошибка `400`. Так прямой POST в `/api/auth/sign-in/magic-link` проходит те же проверки, что и форма.
- `sendMagicLink({ email, url, token })`: в транзакции под `pg_advisory_xact_lock(hashtext(email))` считает письма на эту почту за последние 10 минут в таблице `login_email_sends`. Три и больше - удаляет только что созданный токен и бросает ошибку `429`. Иначе записывает отправку, удаляет все прежние токены этой почты (кроме только что созданного) и отправляет письмо. Блокировка по почте не даёт двум одновременным запросам проскочить лимит.
- Форма входа - server action `requestLoginLinkAction`: сначала та же `parseLoginEmail` (ошибка «Проверьте адрес почты» без запроса к Better Auth), затем `auth.api.signInMagicLink` с `callbackURL: "/"` и `errorCallbackURL: "/login/expired"`. Ошибку `429` переводит в «Слишком часто, попробуйте через несколько минут», успех - в «Ссылка для входа отправлена на ‹почта›». Ответ не зависит от того, есть ли пользователь.

Таблица `login_email_sends (id, email, sent_at)` с индексом `(email, sent_at)`; записи старше 10 минут для этой почты удаляются при каждом запросе.

Альтернативы: встроенный rate limit Better Auth считает по IP и пути, не по почте - не подходит. Считать по таблице `verification` нельзя: прежние токены удаляются при новом запросе.

### 3. Письма: Nodemailer + одна настройка `SMTP_URL`

`src/lib/mailer.ts` создаёт транспорт Nodemailer из строки `SMTP_URL`:

- локально и в тестах - `smtp://localhost:1025` (Mailpit);
- на сервере - SMTP Resend: `smtps://resend:<ключ>@smtp.resend.com:465`.

Так «куда слать» решает настройка, код один. Отправитель «Личная CRM» `<noreply@mail.crm.lyna.tech>` и тема - в коде, они одинаковы везде. Письмо - HTML и текстовая версия: кнопка «Войти», «Ссылка работает 15 минут», «Если вы не запрашивали вход - просто проигнорируйте письмо». В HTML письма CSS-переменные не работают, поэтому цвет кнопки - значение из `tokens.css`, продублированное константой с комментарием (исключение из правила токенов только для письма).

Альтернатива - SDK Resend: тогда локально нужен второй путь отправки. Спека требует одну библиотеку - Nodemailer.

### 4. Где проверяется вход

- `src/proxy.ts`: быстрый редирект на `/login`, если нет cookie сессии (`getSessionCookie`). Пропускает `/login`, `/login/expired`, `/api/auth/*`, `/health`, статику. Это только удобство, не защита.
- Защита - `requireUser()` (`src/lib/session.ts`, `server-only`): `auth.api.getSession({ headers })`, нет сессии - `redirect("/login")`. Вызывается в layout закрытых страниц, в каждой странице, которая читает данные, и первой строкой в каждом server action.
- Маршруты разделены группами: `src/app/(app)/...` - закрытые страницы (адреса не меняются) с layout, где шапка с почтой и «Выйти»; `src/app/(auth)/login`, `src/app/(auth)/login/expired` - без них. Вошедший на `/login` уходит на `/`.
- «Выйти» - server action `signOutAction`: `auth.api.signOut`, затем `redirect("/login")`.

### 5. Владелец в каждом запросе к базе

- `contacts.user_id` и `groups.user_id` - `text not null references "user"(id) on delete cascade`, индексы по `user_id`. Уникальность групп - `uniqueIndex(user_id, lower(name))` вместо `groups_name_lower_idx` (код ошибки дубликата в `groups.ts` проверяет новое имя индекса).
- Все функции `src/db/contacts.ts` и `src/db/groups.ts` получают `userId` первым аргументом и добавляют `user_id = userId` в каждый `where`, в том числе в обновление, удаление, отметку «связались» и её отмену. Чужой номер даёт тот же результат, что несуществующий (`null` / `false`).
- `saveContactGroups` вставляет связи только с группами, где `groups.user_id = userId`: чужая группа молча пропускается, как удалённая.
- Счётчики групп, фильтр, блок «Пора связаться» идут через те же функции - фильтр по владельцу в них.
- Страница контакта: `getContact(userId, id)` вернул `null` - `notFound()`; рядом `contacts/[id]/not-found.tsx` с заголовком «Контакт не найден» (и для чужого, и для удалённого).

Альтернатива - Row Level Security в Postgres: сильнее, но требует своей роли и `set_config` на каждый запрос через пул соединений; для этого размера приложения - лишняя сложность.

### 6. Миграция существующих данных: почта владельца из `OWNER_EMAIL`

Одна миграция drizzle-kit, дописанная вручную:

1. создать таблицы Better Auth и `login_email_sends`;
2. добавить `user_id` в `contacts` и `groups` без `not null`;
3. если в `contacts` или `groups` есть строки: проверить, что задана почта владельца (иначе `raise exception` - миграция падает, транзакция откатывается, новая версия не стартует); создать пользователя с этой почтой (`email_verified = true`, `name = ''`), если его нет; проставить его `id` во все строки `contacts` и `groups`;
4. `set not null`, заменить уникальный индекс групп, добавить индексы.

Почта попадает в SQL так: `migrate.ts` читает `OWNER_EMAIL`, приводит к `trim().toLowerCase()` и до `migrate()` выполняет `select set_config('app.owner_email', $1, false)` на том же единственном соединении. Миграция читает `current_setting('app.owner_email', true)`. На пустой базе (тесты, CI) настройка не нужна, пользователь не создаётся.

`contact_groups` и заметки (поле `notes` контакта) не меняются: они принадлежат владельцу контакта.

`seed.ts` тоже читает `OWNER_EMAIL`, создаёт пользователя, если его нет, и создаёт демо-контакты и группы у него; пропускает работу, если у владельца уже есть контакты.

Альтернативы: почта в коде миграции - попадёт в публичный репозиторий; отдельный скрипт «присвоить данные» после миграции - нужен двухшаговый `not null` и ещё один шаг выкатки.

### 7. Настройки

| Настройка | Локально (`.env`) | Тесты и CI | Сервер (`.env`) |
| --- | --- | --- | --- |
| `BETTER_AUTH_SECRET` | случайная строка | тестовое значение в workflow | случайная строка |
| `BETTER_AUTH_URL` | `http://localhost:3000` | `http://localhost:3200` (e2e) | `https://app.lyna.tech` |
| `SMTP_URL` | `smtp://localhost:1025` | `smtp://localhost:1025` | SMTP Resend с ключом |
| `OWNER_EMAIL` | ваша почта | не нужна | ваша почта |

`.env.example` - те же имена без значений. `deploy/compose.yml`: первые три - сервису `app`, `OWNER_EMAIL` - сервису `migrate` (и для запуска seed). Все через `${VAR:?...}`, кроме `OWNER_EMAIL` у миграции (на пустой базе она не нужна, а на непустой миграция сама упадёт с понятной ошибкой).

Mailpit: сервис `mailpit` в `docker-compose.yml` (порты `127.0.0.1:1025` SMTP и `127.0.0.1:8025` страница); в CI - service container в job `e2e`.

### 8. Тексты и экраны

- Все тексты входа на «вы» (решение владельца): «Проверьте адрес почты», «Слишком часто, попробуйте через несколько минут», «Ссылка устарела, запросите новую». Подсказка пустого списка остаётся «Контактов пока нет. Добавьте первый.».
- Страница входа: заголовок «Вход», поле «Почта», кнопка «Получить ссылку». После отправки плашка «Ссылка для входа отправлена на ‹почта›» над формой; форма остаётся, чтобы исправить опечатку или запросить ссылку ещё раз.
- `/login/expired`: «Ссылка устарела, запросите новую» и кнопка «Войти снова» на `/login`. Показывается при любой ошибке проверки ссылки.
- Шапка: логотип слева, справа почта (обрезается многоточием на узком экране) и кнопка «Выйти». Цвета и отступы - токены.

### 9. Тесты

- Vitest (настоящая база `*_test`, по TDD):
  - `parseLoginEmail`: пробелы, регистр, неверные адреса;
  - слой данных с двумя пользователями: список, счётчик, поиск, «Пора связаться», группы со счётчиками, чужие номера в `get/update/delete/mark/unmark/rename/deleteGroup`, чужая группа в `saveContactGroups`, одинаковое имя группы у разных пользователей и дубль у одного;
  - лимит писем: 3 проходят, 4-й нет, другой регистр не обходит, другой адрес не затронут, записи старше 10 минут не считаются (время отправки задаётся в базе);
  - миграция: база на предыдущей миграции с контактами, группами и связями → применить новую с почтой владельца → те же количества, всё у владельца; без почты на непустой базе - ошибка; на пустой базе - без пользователя.
- Playwright (Mailpit, без моков):
  - `e2e/mailpit.ts`: очистка ящика, поиск последнего письма на адрес, ссылка из письма;
  - `e2e/two-users.spec.ts`: критерий успеха A/B в обе стороны - ни A, ни B не видят контактов и групп друг друга (список, поиск, счётчик, страница «Группы», фильтр, прямая ссылка → «Контакт не найден»);
  - `e2e/login.spec.ts`: письмо (отправитель, тема, тексты); выход; повторная ссылка; старая ссылка после новой; просроченная ссылка (срок токена сдвигается в базе); неверная почта; лимит; первый вход - пустой список; «Слишком часто».
  - существующие `main-scenario.spec.ts`, `keep-in-touch.spec.ts`: вход перед сценарием; шаг «другой браузер» входит под тем же пользователем; `resetDatabase` создаёт тестового пользователя и его контакты.

## Risks / Trade-offs

- [Миграция меняет все существующие строки] → бэкап перед выкаткой уже делает `deploy.sh`; тест миграции на базе с данными; SQL миграции показать владельцу до merge; откат только парой «база из бэкапа + прошлая версия», описан в README.
- [На сервере забыли строки в `.env`] → `compose.yml` с `:?` и миграция с `raise exception` останавливают выкатку до старта новой версии; старая продолжает работать.
- [Домен `mail.crm.lyna.tech` не подтверждён в Resend] → письма на сервере не уйдут, войти будет нельзя. DNS и подтверждение делает владелец до merge; проверка - письмо на сервере после выкатки.
- [Почтовые программы с проверкой ссылок открывают ссылку до человека и «съедают» одноразовый токен] → для Gmail/Яндекса не характерно; если проявится - отдельная правка: страница «Нажмите, чтобы войти» перед входом.
- [Продление входа не чаще раза в сутки] → «30 дней с последнего захода» с точностью до суток; приемлемо.
- [Next.js держит посещённые страницы в клиентском кэше] → выход через `redirect` в server action сбрасывает кэш роутера; закрытые страницы динамические (читают cookie).

## Migration Plan

До merge (делает владелец, агент подсказывает команды):

1. Resend: аккаунт, домен `mail.crm.lyna.tech`, записи DNS, API-ключ.
2. На сервере в `/opt/crm/prod/.env` добавить `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `SMTP_URL`, `OWNER_EMAIL`.
3. Посмотреть SQL миграции.

Выкатка - обычная: бэкап → миграция (данные переходят владельцу) → новый образ → smoke `/health` (без входа отвечает как раньше).

После выкатки: войти под `OWNER_EMAIL` - те же контакты и «Всего», что до выкатки; войти под другой почтой - пусто.

Откат (запускает владелец), только вместе и в таком порядке:

1. `rollback.sh` - запускает прошлую версию приложения (сам снимет ещё один бэкап - он не нужен).
2. `restore.sh <файл>` - файл бэкапа, снятый выкаткой входа, то есть с версией до входа в имени (не тот, что снял `rollback.sh`). Restore оставляет текущую версию - теперь это прошлая.

Между шагами прошлая версия работает на новой схеме: создание групп может падать. Это минуты, и данные потом заменяются бэкапом. Порядок записать в README.
