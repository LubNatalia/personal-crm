# Design

## Context

Зачем — см. proposal.md. Что должно работать — см. specs/contact-groups/spec.md и specs/keep-in-touch/spec.md.

Что есть сейчас:

- В базе одна таблица `contacts` (`src/db/schema.ts`). Все запросы к ней — в `src/db/contacts.ts`. Сортировка по имени — `collate "ru-x-icu"`.
- Главная (`src/app/page.tsx`) читает `?q=` из адреса, показывает список, счётчик и блок «Пора связаться». Блок скрыт во время поиска. Постраничного вывода нет: список отдаёт всех найденных сразу.
- Форма контакта одна для нового и существующего контакта (`src/components/contact-form.tsx`). Поля разбирает `parseContactForm` (`src/lib/contact-form.ts`), сохраняют server actions в `src/app/actions.ts`. Next.js 16 с `cacheComponents`: посещённые страницы остаются в DOM скрытыми (React Activity), у формы уже есть обходы для этого: ключ `instance`, перемонтирование `select` по ключу.
- Удаление с подтверждением уже сделано для контакта (`DeleteContactButton`, `AlertDialog`): отсюда образец для удаления группы. Плашка-подтверждение `StatusNotice` пока живёт внутри `src/app/page.tsx`.
- Тестов и тестовой библиотеки нет. CLAUDE.md требует TDD, Vitest и Playwright. По договорённости e2e на Playwright и CI делаем позже, в этой фиче — только Vitest.
- Postgres 18 (`postgres:18-alpine`) локально и на сервере, локаль базы `en_US.utf8`: `lower()` правильно переводит в нижний регистр кириллицу, включая «Ё». Проверено на локальной базе.

## Goals / Non-Goals

**Goals:**

- Связь «многие ко многим» с целостностью на стороне базы: нельзя связать контакт с несуществующей группой; удаление контакта или группы само убирает связи.
- Уникальность названия без учёта регистра обеспечивает база, а не только проверка в коде: так две вкладки не создадут две одинаковые группы.
- Фильтр, счётчик и метки считаются в базе одним-двумя запросами, без загрузки лишнего в приложение.
- Каждое правило из спеки, которое не зависит от вёрстки, закрыто автотестом Vitest. Тест пишется до кода.

**Non-Goals:**

- e2e-тесты на Playwright и CI: позже, отдельной задачей. Вёрстку и поведение в браузере в этой фиче проверяем руками (агент — в браузере).
- Тесты React-компонентов (jsdom, Testing Library): это ещё библиотеки, а вёрстку закроет Playwright.
- Постраничный вывод списка контактов.

## Decisions

### 1. Две новые таблицы: `groups` и `contact_groups`

- `groups`: `id` (identity), `name text not null`, `created_at`, `updated_at`. Уникальный индекс `groups_name_lower_idx` по выражению `lower(name)`.
- `contact_groups`: `contact_id` → `contacts.id`, `group_id` → `groups.id`, оба `on delete cascade`, первичный ключ `(contact_id, group_id)`. Отдельный индекс по `group_id` нужен фильтру: первичный ключ начинается с `contact_id` и для поиска по группе не подходит.

Почему таблица связей, а не массив `group_ids int[]` в `contacts`: у массива нет внешних ключей. Удалённая группа осталась бы в массивах у контактов, чистить пришлось бы вручную.

Почему не текстовые теги у контакта: переименование группы пришлось бы делать по всем контактам, и легко получить «Теннис» и «теннис» как две разные группы.

Почему `lower(name)`, а не тип `citext` или `casefold()`: `citext` — расширение Postgres, его надо включать отдельно. `casefold()` на нашей локали даёт то же, что `lower()`. Отличаться они будут на редких символах вроде немецкой «ß», а групп с такими названиями у нас нет.

### 2. Название группы: проверка в коде, уникальность — в базе

`src/lib/groups.ts`:

- `parseGroupName(raw)`: обрезает пробелы по краям. Пусто → «Укажите название». Больше 50 символов → «Слишком длинно: максимум 50 символов». Внутренние пробелы не трогает.
- `GROUP_NAME_MAX_LENGTH = 50`. Предел выбран так, чтобы метка помещалась в строку на телефоне.
- `formatContactCount(n)` → «1 контакт», «3 контакта», «5 контактов», «21 контакт» — через `Intl.PluralRules`, как `formatDayCount`.

`src/db/groups.ts`: `createGroup(name)` и `renameGroup(id, name)` ловят ошибку Postgres `23505` (нарушение уникальности) именно на индексе `groups_name_lower_idx`. В этом случае они возвращают результат «такая группа уже есть», а не бросают исключение. Проверять заранее запросом «нет ли такой» не нужно: между проверкой и вставкой могла успеть другая вкладка.

Переименование «теннис» → «Теннис» проходит само: индекс сравнивает с другими строками, а не с этой же.

### 3. Запросы к базе

`src/db/groups.ts`:

- `listGroups()`: `id`, `name` по алфавиту (`name collate "ru-x-icu"`, затем `id`). Нужен для фильтра, меток и поля в форме.
- `listGroupsWithCounts()`: то же плюс число контактов — `left join contact_groups … group by`. Нужен для страницы «Группы».
- `createGroup`, `renameGroup`, `deleteGroup`. `deleteGroup` возвращает название удалённой группы или `null`, если её уже нет, — как `deleteContact`.

`src/db/contacts.ts`:

- `listContacts(nameQuery, groupId)`: фильтр по группе — `exists (select 1 from contact_groups where contact_id = contacts.id and group_id = $1)`. Каждая строка получает `groupIds` — `array(select group_id from contact_groups where contact_id = contacts.id)`. Названия меток подставляет страница из `listGroups()`, в его порядке, то есть по алфавиту. Так в каждой строке из 1000 не повторяются названия групп.
- `countContacts(groupId?)`: всего или в группе.
- `getContact(id)` дополнительно возвращает `groupIds` контакта.
- `createContact` и `updateContact` сохраняют группы в той же транзакции, что и поля. Сначала удаляются связи, которых нет в новом списке. Потом добавляются новые: `insert … select id from groups where id = any($ids) on conflict do nothing`. Группа, которую успели удалить в другой вкладке, молча пропускается, ошибки нет. `createContact` переводится в транзакцию: раньше это был один `insert`.

### 4. Поле «Группы» в форме — нативные чекбоксы

- Каждая метка — `<label>` с `<input type="checkbox" name="groupIds" value={id} class="sr-only peer">` внутри. Вид метки зависит от состояния чекбокса: отмечено — фон `accent`, белый текст, значок `Check`; не отмечено — белый фон, рамка `lavender-200`. Фокус с клавиатуры — та же обводка `outline-accent`, что у остальных полей. Зона нажатия не меньше 44 px. Метки обёрнуты в `<fieldset>` с `<legend>Группы</legend>`.
  Почему нативные чекбоксы, а не свой компонент на Base UI: значения сами попадают в `FormData` (`getAll("groupIds")`), пробел и Tab работают без кода, а `defaultChecked` ведёт себя так же, как `defaultValue` у остальных полей. Это важно из-за React Activity.
- `parseContactForm` разбирает `getAll("groupIds")`: каждое значение — целое положительное число, повторы убираются. Если значение не такое (подделанный запрос), — ошибка поля «Выберите группы из списка». В `ContactValues` добавляется `groupIds: string[]`, чтобы после ошибки в другом поле отметки не терялись. В `ContactInput` — `groupIds: number[]`.
- После неудачного сохранения форма показывает отправленные значения. Чтобы чекбоксы подхватили новые `defaultChecked`, группа меток перемонтируется по ключу из отмеченных id — тот же приём, что у `select` частоты.
- Место — во всю ширину под сеткой полей, над «Заметками».

### 5. «Новая группа» внутри формы контакта

- Кнопка «Новая группа» (`type="button"`) открывает поле и кнопку «Создать». Это не вложенная форма: HTML не разрешает форму внутри формы. Поле без `name`, поэтому не уходит вместе с контактом. Enter в поле перехватывается (`preventDefault`) и создаёт группу, а не отправляет форму контакта. Escape закрывает поле.
- «Создать» вызывает server action `createGroupAction(name)`. Он возвращает `{ ok: true, group }` или `{ ok: false, error }`. Ошибка показывается под полем названия.
- После успеха компонент запоминает id новой группы как «отметить при появлении». Server action обновляет страницу, новая метка приходит с сервера и монтируется с `defaultChecked`. Ключ формы не меняется, поэтому несохранённые правки в остальных полях остаются, как и с галочкой «Связались».
- Группа создаётся сразу, ещё до «Сохранить». Так проще и понятнее: «Создать» действительно создаёт. Если контакт не сохранили, группа остаётся пустой (сценарий есть в спеке).

### 6. Страница «Группы» — `/groups`

- Серверная страница: `listGroupsWithCounts()`, ссылка «← Все контакты», заголовок «Группы».
- Форма создания — клиентский компонент на `useActionState`, как форма контакта. После успеха поле очищается, после ошибки текст остаётся.
- Строка группы: название, «N контактов», ссылка «Показать» (на главную с этим фильтром), кнопки «Переименовать» и «Удалить».
  - Переименование — в той же строке: поле, «Сохранить», «Отмена».
  - Удаление — `AlertDialog`, по образцу `DeleteContactButton`, включая закрытие окна при уходе со страницы. После удаления — переход на `/groups?deleted=<название>` и плашка «Группа «…» удалена.». Если группы уже нет — `/groups` без плашки.
  - Переименование группы, которую удалили в другой вкладке: переход на `/groups` без ошибки — в списке её уже нет.
- `StatusNotice` переезжает из `src/app/page.tsx` в `src/components/status-notice.tsx`, чтобы им пользовались обе страницы.
- Кнопка «Группы» на главной — рядом с «Добавить контакт», вариант `outline`, иконка `Tags` из `lucide-react`. На телефоне обе кнопки во всю ширину, одна под другой.

### 7. Главная: фильтр, метки, счётчик

- Адрес: `/?group=<id>`, вместе с поиском — `/?q=Ан&group=3`. Сначала страница загружает `listGroups()`: запрос маленький. Затем проверяет `group`. Если такой группы нет или значение не число, фильтр не применяется и выбрано «Все». После этого параллельно идут список, счётчик и (без поиска и без группы) блок «Пора связаться».
- Ряд фильтра — ссылки, а не кнопки: выбор меняет адрес. Ряд обёрнут в `<nav aria-label="Фильтр по группе">`, у выбранной ссылки `aria-current="page"`. Ссылки сохраняют `q`. Ряд переносится на несколько строк (`flex-wrap`), горизонтальной прокрутки нет. Без групп ряда нет.
- Форма поиска хранит группу скрытым полем `group`. «Сбросить» ведёт на `/?group=<id>` (или `/`, если группа не выбрана).
- Метки в строке — под именем, в ячейке «Имя», на всех ширинах экрана. Это не ссылки: имя уже ссылка на карточку. Вид — как плашки в блоке «Пора связаться»: `rounded-chip`, `bg-lavender-100`, `text-ink-muted`, размер `text-12`/`text-13`.
- Тексты счётчика и пустого списка — чистые функции в `src/lib/contact-list.ts`: `formatListSummary` («Всего: N», «Найдено: X из N», «В группе «…»: N») и `formatEmptyListMessage` (четыре варианта: нет контактов, никого по запросу, пустая группа, никого по запросу в группе). Их легко покрыть тестами.

### 8. Обновление страниц после изменений

- Создание, переименование и удаление группы меняют главную, карточки контактов, «Новый контакт» и «Группы». Поэтому эти действия вызывают `revalidatePath("/", "layout")`: по документации Next.js 16 это обновляет все страницы под корневым layout.
- Сохранение и удаление контакта дополнительно вызывают `revalidatePath("/groups")`: там меняются счётчики.
- Страница «Новый контакт» теперь читает список групп из базы, то есть становится динамической, как главная.

### 9. Блок «Пора связаться» при фильтре

На главной `listDueContacts()` вызывается, только когда нет ни поиска, ни выбранной группы. Это ровно изменённое требование «Когда блок скрыт».

### 10. Тестовые данные

`src/db/seed.ts` (только при пустой таблице `contacts`):

- после контактов и частот (их порядок и зерно не меняются, данные остаются прежними) создаёт группы «Семья», «Друзья», «Знакомые», «Теннис», «Аналитики». Группа, которая уже есть, не дублируется (`on conflict do nothing`);
- раскладывает по ним примерно 40 % контактов в одну группу и 10 % в две.

### 11. Автотесты: Vitest

- Пакеты `vitest` и `vite` (обязательный партнёр Vitest 5) — последние стабильные на момент установки. Сейчас это `vitest@5.0.5` и `vite@8.3.5`. Перед установкой версии проверяются заново.
- `vitest.config.mts`:
  - алиас `@` → `./src` вручную, без пакета `vite-tsconfig-paths`;
  - алиас `server-only` → пустой модуль: настоящий бросает ошибку вне сервера Next.js;
  - окружение `node`;
  - тестовые файлы выполняются по одному (`fileParallelism: false`), потому что тестовая база одна.
- Команда `pnpm test` = `vitest run`: один прогон, без режима наблюдения.
- Два вида тестов, файлы `*.test.ts` рядом с кодом:
  - чистые функции (`src/lib/*.test.ts`): `parseGroupName`, `formatContactCount`, разбор `groupIds` в `parseContactForm`, `formatListSummary`, `formatEmptyListMessage`;
  - запросы к базе (`src/db/*.test.ts`) — на настоящем Postgres, без моков.
- Тестовая база — в том же локальном Postgres в Docker. Её имя = имя базы из `DATABASE_URL` + `_test`. Её адрес вычисляется в `vitest.config.mts` и передаётся тестам как `DATABASE_URL`. Новых строк в `.env` не нужно.
  - Глобальная подготовка (`globalSetup`) создаёт базу, если её нет, и применяет миграции Drizzle — тем же `migrate()`, что и `src/db/migrate.ts`.
  - Перед каждым тестом таблицы очищаются (`truncate … restart identity cascade`).
  - Защита: функция очистки сначала проверяет `current_database()`. Если имя не кончается на `_test`, тест падает, ничего не удалив. Рабочая локальная база с тестовыми контактами не трогается никогда.
- `pnpm test` требует запущенной базы (`docker compose up -d`). Это пишется в README.
- Сервер выкатки, компоненты и страницы автотестами в этой фиче не покрываются. Server actions — тонкие обёртки над проверенными функциями `src/lib` и `src/db`, их поведение проверяется в браузере.

## Risks / Trade-offs

- [Группу создали из карточки, а контакт не сохранили — остаётся пустая группа] → так решено; её видно на странице «Группы» с «0 контактов», удалить — одна кнопка.
- [Чужие изменения групп при открытой форме: группу удалили в другой вкладке, а здесь она отмечена] → при сохранении удалённая группа молча пропускается, остальное сохраняется.
- [`revalidatePath("/", "layout")` обновляет все страницы, включая главную с отмеченными галочками в блоке] → блок уже умеет держать отмеченные строки при обновлении данных страницы (`withTickedRows`).
- [`lower()` зависит от локали базы] → локаль `en_US.utf8` одинаковая локально и на сервере (тот же образ). Тест «ТЕННИС» / «теннис» гоняется на такой же базе.
- [Без постраничного вывода у 1000 контактов к каждой строке добавляется подзапрос групп] → подзапрос идёт по индексу первичного ключа `contact_groups`. Если список станет медленным — постраничный вывод отдельной задачей.
- [Тесты очищают таблицы] → только в базе `*_test`; проверка имени базы стоит до очистки.
- [Длина названия 50 символов — моё решение] → поменять — одна константа.
- [Откат на предыдущий образ после миграции] → старый код новых таблиц не знает и не ломается. Группы, созданные на новой версии, остаются в базе и вернутся при следующей выкатке. Миграция при откате не отменяется (как и раньше).

## Migration Plan

1. `pnpm db:generate` создаёт миграцию: `CREATE TABLE groups`, уникальный индекс по `lower(name)`, `CREATE TABLE contact_groups` с внешними ключами и индексом по `group_id`. Таблица `contacts` не меняется.
2. Выкатка обычная: merge в main → образ → разовый контейнер с миграциями → новый образ → smoke `/health`.
3. Откат — только вручную, `rollback.sh` (см. Risks).
