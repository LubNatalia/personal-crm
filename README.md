# Личная CRM

Приложение, где я веду контакты людей, которых знаю лично. Подробнее - `specs/01-продуктовая-идея.md`. Пользователи и вход - `specs/02-пользователи-вход.md`.

## Как запустить

### Что нужно установить

- Docker Desktop
- Node.js 24 и pnpm

### Первый запуск

1. Создайте файл `.env` по образцу `.env.example` и заполните значения: логин, пароль, имя базы, порт и строку подключения `DATABASE_URL`. Для входа нужны ещё четыре строки:

   - `BETTER_AUTH_SECRET` - любая случайная строка не короче 32 символов (ею подписывается вход). Получить такую: `node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"`
   - `BETTER_AUTH_URL=http://localhost:3000` - адрес приложения (ссылки в письмах ведут на него)
   - `SMTP_URL=smtp://localhost:1025` - куда отправлять письма: в почтовую заглушку Mailpit (см. «Как войти локально»), настоящие письма никуда не уходят
   - `OWNER_EMAIL` - ваша настоящая почта: под ней вы входите, и ей достаются контакты и группы, которые уже есть в базе (и тестовые данные из шага 5)

2. Установите зависимости:

   ```
   pnpm install
   ```

3. Запустите базу данных и почтовую заглушку Mailpit:

   ```
   docker compose up -d
   ```

4. Создайте таблицы в базе. Если в базе уже есть контакты (с времён до входа), миграция отдаст их пользователю с почтой `OWNER_EMAIL`; без этой строки она остановится с ошибкой и ничего не изменит:

   ```
   pnpm db:migrate
   ```

5. Если нужно, заполните базу тестовыми данными (1000 контактов). Примерно у каждого десятого задана частота общения и даты в последние месяцы, поэтому на главной сразу виден блок «Пора связаться», а у части контактов срок ещё не вышел. Ещё создаётся пять групп: «Семья», «Друзья», «Знакомые», «Теннис», «Аналитики». Примерно 40 % контактов лежат в одной группе, примерно 10 % - сразу в двух. Всё это создаётся у пользователя с почтой `OWNER_EMAIL` (если такого пользователя нет, он создаётся). Команда срабатывает, только если у этого пользователя ещё нет контактов:

   ```
   pnpm db:seed
   ```

6. Соберите и запустите приложение:

   ```
   pnpm build
   pnpm start
   ```

7. Откройте в браузере http://localhost:3000 и войдите (см. «Как войти локально»).

### Следующие запуски

1. `docker compose up -d` - запустить базу и Mailpit (если Docker Desktop перезапускался, они поднимутся сами).
2. `pnpm start` - запустить приложение.
3. Открыть http://localhost:3000 и войти.

Остановить приложение: закрыть окно, в котором оно запущено, или нажать Ctrl+C.

### Как войти локально

Паролей нет: вход по ссылке из письма. Локально письма не уходят настоящим адресатам, их ловит Mailpit.

1. Откройте http://localhost:3000 - увидите страницу входа.
2. Введите почту и нажмите «Получить ссылку». Под любой почтой можно войти: первый вход и есть регистрация. Чтобы увидеть свои контакты и тестовые данные, введите почту из `OWNER_EMAIL`.
3. Откройте http://localhost:8025 - это ящик Mailpit. Откройте письмо «Вход в Личную CRM» и нажмите «Войти».
4. Откроется приложение, в шапке - ваша почта и кнопка «Выйти».

Ссылка одноразовая и живёт 15 минут; новый запрос отменяет прежние ссылки; на одну почту уходит не больше 3 писем за 10 минут. Вход держится 30 дней с последнего захода. Чтобы проверить, как видят приложение двое, войдите под второй почтой в другом браузере или в окне инкогнито.

### Режим разработки

`pnpm dev` - приложение с автоматической перезагрузкой при изменении кода.

### База данных

- Проверить, что база работает: `docker compose ps`, в колонке STATUS должно быть `healthy`.
- Остановить базу: `docker compose stop`. Данные при этом сохраняются.
- Внимание: команда `docker compose down -v` удаляет все данные базы.
- Схема таблиц - `src/db/schema.ts`. После её изменения: `pnpm db:generate` (создать миграцию), затем `pnpm db:migrate` (применить).
- Mailpit (ящик с письмами входа) - http://localhost:8025. Остановить вместе с базой: `docker compose stop`.

### Автотесты

- `pnpm test` - прогнать все автотесты один раз.
- Нужны запущенные база и Mailpit: `docker compose up -d` (тесты входа читают письма из Mailpit и очищают его ящик).
- Тесты, которым нужна база, работают в отдельной базе `<имя базы>_test` (например, `personal_crm_test`) в том же Postgres. Она создаётся сама при первом запуске, к ней применяются миграции, а перед каждым тестом её таблицы очищаются.
- Рабочие данные тесты не трогают: очистка отказывается работать на любой базе, имя которой не кончается на `_test`.

### e2e-тесты (проверка в настоящем браузере)

- `pnpm test:e2e` - собрать приложение, запустить его на http://localhost:3200 и пройти сценарии в браузере: вход по ссылке из письма (письма читаются из Mailpit), главный сценарий (открыть список, добавить контакт, найти его, дописать заметку, проверить, что она сохранилась и видна из другого браузера), «Пора связаться» и проверка, что двое пользователей не видят данные друг друга.
- Нужны запущенные база и Mailpit: `docker compose up -d`. Пока идут тесты, не пользуйтесь Mailpit руками: тесты очищают его ящик.
- Один раз на компьютере нужно скачать браузер для тестов: `pnpm exec playwright install chromium`.
- Тесты работают в своей базе `<имя базы>_e2e_test` (например, `personal_crm_e2e_test`). Перед каждым тестом она очищается и в неё кладутся тестовый пользователь `tester@example.com` и два его контакта.
- Порт 3200 должен быть свободен. Команда сама пересобирает приложение, поэтому запущенный рядом `pnpm start` после неё лучше перезапустить.
- Если тест упал, в папке `test-results` лежит запись прохождения. Посмотреть её: `pnpm exec playwright show-trace test-results\<папка теста>\trace.zip`.

### Оформление и проверки кода

- `pnpm format` - выровнять оформление кода (Prettier): отступы, переносы, кавычки. Логику не меняет.
- `pnpm format:check` - проверить оформление, ничего не меняя.
- `pnpm lint` - проверить код на типичные ошибки (ESLint).
- `pnpm typecheck` - проверить типы TypeScript.

### Проверки на каждый PR

На каждый PR в `main` GitHub Actions (`.github/workflows/ci.yml`) запускает:

- lint, оформление, типы и автотесты Vitest;
- e2e-тесты Playwright в настоящем браузере на настоящей базе; письма входа ловит Mailpit, запущенный рядом (service container), настоящие письма не уходят;
- сборку Docker-образа приложения (без выкладки в GHCR).

Ход проверок - внизу страницы PR и во вкладке Actions. Если упали e2e-тесты, запись прохождения лежит в архиве `playwright-traces` на странице запуска.

## Как выкатить

Приложение работает на сервере в двух окружениях. На тест-стенд новая версия выкатывается сама после каждого влития в `main`. На прод - только когда вы нажмёте кнопку, и только версия, которая уже успешно выкатилась на тест-стенд.

|                            | Прод                               | Тест-стенд                                         |
| -------------------------- | ---------------------------------- | -------------------------------------------------- |
| Адрес                      | https://app.lyna.tech              | https://test-app.lyna.tech (под логином и паролем) |
| Как выкатывается           | кнопкой Deploy prod                | сам после влития в `main` (Deploy staging)         |
| Папка на сервере           | `/opt/crm/prod`                    | `/opt/crm/staging`                                 |
| Проект docker compose      | `prod`                             | `staging`                                          |
| Порт приложения на сервере | `127.0.0.1:3000`                   | `127.0.0.1:3001`                                   |
| База                       | своя                               | своя: копия базы прода из бэкапа                   |
| `.env` и ключи             | свои                               | свои, свой ключ Resend                             |
| Бэкапы                     | ежедневно в 03:00 и перед выкаткой | нет                                                |

### Выкатить на тест-стенд

1. Закоммитьте изменения в отдельную ветку, сделайте push и откройте PR в `main`. Напрямую в `main` push не пройдёт: ветка защищена.
2. CI проверяет PR (см. «Проверки на каждый PR»). Все проверки зелёные - PR с включённым автовлитием вливается в `main` сам. Хоть одна красная - не вливается.
3. После влития запускается «Deploy staging»: https://github.com/LubNatalia/personal-crm/actions/workflows/deploy-staging.yml (зелёная галочка - выкатилось, красный крестик - упало). Прод при этом не меняется.
4. Проверить: откройте https://test-app.lyna.tech/health - там `"status":"ok"`, а в `"version"` номер (SHA) последнего коммита. Затем проверьте новую версию руками на стенде.

### Выкатить на прод

1. Откройте https://github.com/LubNatalia/personal-crm/actions/workflows/deploy-prod.yml
2. Справа нажмите «Run workflow». Ветка - `main` (с другой ветки запуск сразу остановится).
3. Поле SHA оставьте пустым, галочку rollback не ставьте. Нажмите зелёную «Run workflow».
4. Выкатится версия последней зелёной выкатки на тест-стенд - то есть ровно то, что вы проверили на стенде.
5. Когда запуск станет зелёным, откройте его: в итогах (Summary) написано, какая версия (SHA) теперь на проде.
6. Проверить: https://app.lyna.tech/health - `"status":"ok"`, в `"version"` тот же SHA, что в итогах и на стенде. Откройте https://app.lyna.tech и убедитесь, что всё на месте.

Запасной путь - выкатить конкретную версию: впишите в поле SHA номер коммита (целиком или первые 7 и больше символов). Прод примет его, только если этот коммит успешно выкатывался на тест-стенд; иначе запуск остановится с ошибкой и прод не изменится.

### Откатить прод

Если новая версия на проде плохая, верните ту, что была до неё:

1. https://github.com/LubNatalia/personal-crm/actions/workflows/deploy-prod.yml → «Run workflow», ветка `main`.
2. Поставьте галочку rollback (поле SHA при этом не смотрится) и нажмите «Run workflow».
3. В итогах запуска - SHA версии, на которую откатились; https://app.lyna.tech/health показывает его.

Что важно:

- Откат возвращает версию прода, которая была перед текущей (её помнит сервер, образ хранится там же). Тест-стенд при откате не проверяется.
- Откат - тоже выкатка: перед ним снимается бэкап базы.
- Миграции базы при откате не отменяются: прошлая версия работает на текущей базе. Если выкатка меняла данные, одного отката мало - пример в «Как откатить выкатку входа».
- Повторный откат вернёт ту версию, с которой откатились. Вернуться к свежей версии можно и обычной выкаткой (поле SHA пустое).

### Как это устроено

1. Влитие в `main` → «Deploy staging» (`.github/workflows/deploy-staging.yml`): собирает образ приложения с тегом - SHA коммита - и кладёт его в GitHub Container Registry (GHCR), затем выкатывает этот образ на тест-стенд.
2. Кнопка «Deploy prod» (`.github/workflows/deploy-prod.yml`): по истории запусков Deploy staging выбирает SHA, который прошёл стенд (`deploy/prod-sha.sh`), и выкатывает на прод тот же самый образ, что уехал на стенд. С галочкой rollback - откатывает.
3. Выкатка в обоих случаях - один и тот же скрипт `deploy/ci.sh`, окружение - параметр (`ci.sh staging ...`, `ci.sh prod ...`). Он копирует всю папку `deploy/` на сервер в папку окружения (`/opt/crm/staging` или `/opt/crm/prod`) и запускает там `deploy.sh`:
   - скачивает образ, если его ещё нет на сервере;
   - только на проде: снимает бэкап базы (см. «Бэкапы и восстановление базы»). Бэкап не получился - выкатка останавливается, работает старая версия;
   - применяет миграции базы разовым контейнером из того же образа. Упали миграции - новая версия не запускается, работает старая;
   - запускает новую версию;
   - проверяет, что `/health` отвечает 200 (smoke). Не ответил - выкатка упала, автоматического отката нет;
   - только на проде, после удачной выкатки: ставит ежедневный бэкап в расписание сервера (если его там ещё нет) и удаляет старые образы приложения на сервере - старше 2 недель, кроме текущей и прошлой версии прода и текущей версии стенда. Образы лендинга и прочие чужие образы не трогаются.
4. После удачной выкатки прода Deploy prod чистит GHCR: там остаются 10 последних сборок (`deploy/ghcr-cleanup.sh`).
5. Окружение определяется папкой: скрипты в `/opt/crm/staging` работают только со стендом, в `/opt/crm/prod` - только с продом.
6. Две выкатки одного окружения одновременно не идут: запуски в Actions выстраиваются в очередь, а на сервере скрипты выкатки, отката, восстановления и ежедневного бэкапа берут замок своего окружения (второй ждёт до 10 минут, потом останавливается с ошибкой).
7. На сервере docker compose, проекты `prod` и `staging` - у каждого база PostgreSQL (`db`) и приложение (`app`). nginx отдаёт их наружу.
8. Лимиты памяти: база - 256 МБ, приложение и миграции - 512 МБ, в каждом окружении. Поменять можно строками `DB_MEM_LIMIT=512m` и `APP_MEM_LIMIT=1g` в `.env` окружения, затем выкатить заново.

### Если выкатка упала

- Откройте упавший запуск во вкладке Actions и посмотрите лог красного шага. В итогах запуска написано, какая версия работает сейчас.
- Упал выбор версии («Pick the version») - прод не трогали. Обычно это SHA, который не проходил стенд.
- Упали бэкап или миграции - новая версия не запускалась, работает старая.
- Упал smoke (`/health`) - новая версия запущена, но не отвечает. Сама она не откатывается: откатите прод кнопкой (см. «Откатить прод»).
- Упала только чистка GHCR в конце - выкатка уже прошла, прод работает; чистка повторится при следующей выкатке.
- Тест-стенд откатывается вручную на сервере: `ssh crm`, затем `bash /opt/crm/staging/rollback.sh` - пока прошлый образ стенда ещё лежит на сервере. Проще влить исправление: стенд выкатится сам.

### Логи

Логи контейнеров пишутся в журнал сервера (journald): они переживают выкатку и откат, а размер журнала ограничивает сама система, удаляя старые строки. Читать на сервере (`ssh crm`):

- последние 100 строк приложения: `docker logs --tail 100 prod-app-1` (стенд - `staging-app-1`, база - `prod-db-1`, `staging-db-1`);
- из журнала, в том числе от прошлых версий: `journalctl CONTAINER_NAME=prod-app-1 -n 200 --no-pager`;
- за период: `journalctl CONTAINER_NAME=prod-app-1 --since "2026-11-11 10:00" --until "2026-11-11 12:00" --no-pager`;
- следить в реальном времени: `journalctl CONTAINER_NAME=prod-app-1 -f` (выход - Ctrl+C).

Если `journalctl` пишет, что нет прав, добавьте в начало `sudo`.

### Секреты

- На сервере у каждого окружения свой `.env`, права 600: `/opt/crm/prod/.env` и `/opt/crm/staging/.env`. Создать его: `bash /opt/crm/<окружение>/init-env.sh` (см. «Тест-стенд»). Строки: `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`, `DATABASE_URL` (адрес базы - `db`, не `localhost`), и для входа:
  - `BETTER_AUTH_SECRET` - случайная строка не короче 32 символов, своя для сервера, не такая, как локально;
  - `BETTER_AUTH_URL` - адрес приложения, на него ведут ссылки в письмах: на проде `https://app.lyna.tech`, на стенде `https://test-app.lyna.tech`. Так письмо, запрошенное на стенде, ведёт на стенд, а не на прод;
  - `SMTP_URL=smtps://resend:<API-ключ Resend>@smtp.resend.com:2465` - через что слать настоящие письма (порт 2465, не 465: хостер сервера закрывает исходящие 465, 587 и 25) (см. «Письма входа: Resend»);
  - `OWNER_EMAIL` - ваша настоящая почта. Нужна на выкатке, где данные впервые получают владельца (контакты и группы, созданные до входа, достаются этому пользователю). Если какой-то из первых трёх строк нет, выкатка остановится до запуска новой версии, работать будет старая.
- В GitHub (Settings → Secrets and variables → Actions): секрет `DEPLOY_SSH_KEY` - ключ, которым выкатка заходит на сервер; переменные `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_KNOWN_HOSTS`.

### Полезные команды на сервере

- Что запущено: `docker ps`
- Сколько памяти занято и какие лимиты: `docker stats --no-stream`
- Логи - см. «Логи»
- Пересоздать приложение стенда после правки его `.env`: `cd /opt/crm/staging && APP_PORT=3001 APP_IMAGE=$(cat current-image) docker compose -p staging -f compose.yml up -d --force-recreate app`
- Тестовые данные (создаются у пользователя `OWNER_EMAIL`, срабатывают, только если у него ещё нет контактов): `cd /opt/crm/prod && APP_IMAGE=$(cat current-image) docker compose -p prod -f compose.yml run --rm migrate node db/seed.ts`

## Тест-стенд

https://test-app.lyna.tech - копия прода, чтобы проверять новую версию на настоящих данных до того, как она понадобится на проде. Выкатывается сама при каждом влитии в `main` (см. «Выкатить на тест-стенд»); на прод попадает только версия, прошедшая стенд.

- Весь сайт закрыт логином и паролем (браузер спросит их один раз).
- База своя, это копия базы прода из последнего бэкапа. Изменения на стенде на прод не попадают.
- Письма входа настоящие, уходят через свой ключ Resend; ссылка в письме ведёт на стенд.
- Вход на стенде и на проде разный: кука входа живёт только на своём адресе, войти на стенде не значит войти на проде.

### Обновить данные стенда из прода

Если данные стенда испортились или нужны свежие, загрузите в него последний бэкап прода (база стенда удаляется и создаётся заново, прод не затрагивается):

```
ssh crm
bash /opt/crm/staging/refresh-staging-db.sh
```

Скрипт покажет, какой бэкап и какую базу затрагивает, и попросит ввести `yes`. Нужен свежий бэкап - сначала снимите его: `bash /opt/crm/prod/backup.sh`.

### Как стенд поднят (один раз, руками)

1. DNS: у регистратора домена `lyna.tech` - запись A `test-app` → IP сервера (тот же, что у `app`).
2. Ключ Resend для стенда: в Resend API Keys → Create API Key (права на отправку), назвать, например, `crm-staging`. Домен отправителя тот же, `mail.crm.lyna.tech`.
3. Папка и `.env` стенда. Скрипты копируются с компьютера из папки проекта, затем `.env` создаётся на сервере (ключ Resend вводится скрыто, пароль базы и секрет входа генерируются сами):

   ```
   ssh crm "sudo install -d -o crmapp -g crmapp -m 750 /opt/crm/staging"
   scp deploy/* crm:/opt/crm/staging/
   ssh -t crm "bash /opt/crm/staging/init-env.sh"
   ```

4. Пароль на сайт - логин любой, пароль вводится скрыто, дважды:

   ```
   printf 'ЛОГИН:%s\n' "$(openssl passwd -apr1)" | sudo tee /etc/nginx/htpasswd-test-app >/dev/null
   ```

   Поменять пароль - та же команда.

5. nginx и сертификат - команды в начале `deploy/nginx-staging.conf`. У стенда свой сайт в nginx (`/etc/nginx/sites-available/test-app.lyna.tech`) и свой сертификат (`/etc/letsencrypt/live/test-app.lyna.tech`), настройки прода и лендинга не меняются. Сертификат продлевается сам, как у прода.
6. Первая выкатка - любое влитие в `main` (или Actions → Deploy staging → Run workflow), затем копия данных: `bash /opt/crm/staging/refresh-staging-db.sh`.

## Письма входа: Resend

На сервере письма со ссылкой для входа уходят настоящим адресатам через сервис Resend (SMTP). Отправитель - «Личная CRM» `<noreply@mail.crm.lyna.tech>`: домен `mail.crm.lyna.tech` должен быть подтверждён в Resend, иначе письма не дойдут и войти будет нельзя.

Что сделать один раз (руками, до выкатки):

1. Завести аккаунт на https://resend.com.
2. В Resend: Domains → Add Domain → `mail.crm.lyna.tech`. Resend покажет записи DNS (обычно MX и TXT для SPF и DKIM).
3. Добавить эти записи в DNS домена `lyna.tech` у регистратора и дождаться статуса «Verified» в Resend.
4. В Resend: API Keys → Create API Key (права на отправку). Ключ показывается один раз.
5. Дописать строки в `/opt/crm/prod/.env` на сервере (см. «Секреты»), не показывая ключ в чате и не кладя его в git. Порт в `SMTP_URL` - `2465`: на этом сервере исходящие 465, 587 и 25 закрыты (`Connection timeout` в логе), а 2465 и 2587 открыты. `OWNER_EMAIL` - только сам адрес, без `<` и `>` и без пояснений: по нему миграция отдаёт владельцу все существующие данные, и опечатка отдаст их не тому пользователю.
   После правки `.env` приложение нужно пересоздать, иначе оно работает со старыми значениями: `cd /opt/crm/prod && APP_IMAGE=$(cat current-image) docker compose -p prod -f compose.yml up -d --force-recreate app`.
6. Проверить после выкатки: откройте https://app.lyna.tech, введите свою почту, письмо должно прийти в настоящий ящик (проверьте и «Спам»).

## Как откатить выкатку входа

Эта выкатка меняет данные в базе (всем контактам и группам проставляется владелец), поэтому откатывать её нужно только парой шагов и именно в таком порядке. Один откат без бэкапа не годится: прошлая версия приложения не умеет работать с владельцами и не сможет создавать группы и контакты.

1. Вернуть прошлую версию приложения: Deploy prod с галочкой rollback (см. «Откатить прод»). Откат сам снимет ещё один бэкап (с новой структурой) - он для отката не нужен.
2. Восстановить базу из бэкапа, который снят выкаткой входа, то есть перед миграцией: в его имени версия приложения, которая работала до входа (см. «Бэкапы»). Не берите бэкап, снятый шагом 1:

   ```
   ls -lh /opt/crm/prod/backups
   bash /opt/crm/prod/restore.sh /opt/crm/prod/backups/<файл выкатки входа>
   ```

   Restore оставит текущую версию приложения - после шага 1 это прошлая.

Между шагами 1 и 2 прошлая версия работает на новой структуре базы: добавление групп и контактов может падать. Это минуты, и данные потом заменяются бэкапом (всё, что внесено после выкатки входа, пропадёт, но останется в копии `_before-restore`).

## Бэкапы и восстановление базы

### Бэкапы

- Бэкапы есть только у прода. У тест-стенда их нет: его база - копия бэкапа прода.
- Когда снимаются:
  - каждый день в 03:00 по Москве - файлы с `_daily` в конце;
  - перед каждой выкаткой и откатом прода - `_deploy`;
  - перед восстановлением базы (снимает restore) - `_before-restore`;
  - вручную - `_manual`. Старые бэкапы без такой пометки в имени тоже считаются ручными.
- Каждого вида хранятся 7 самых новых, более старые этого же вида удаляются сами после очередного бэкапа. Например, ежедневные - за последнюю неделю, и выкатки их не вытесняют.
- Бэкапы лежат на сервере в `/opt/crm/prod/backups`. Читать их может только владелец папки.
- Имя файла - дата и время (UTC), версия приложения, которая работала в этот момент (SHA коммита, как в `"version"` на https://app.lyna.tech/health), и вид. Например, `2026-11-03_14-05-12_a29a88f..._deploy.dump` - бэкап перед выкаткой 3 ноября в 14:05 UTC, снят, пока работала версия `a29a88f...`.
- Посмотреть список: `ssh crm`, затем `ls -lh /opt/crm/prod/backups`.
- Скачать бэкап на компьютер: `scp crm:/opt/crm/prod/backups/<файл> .` (выполнять на компьютере, не на сервере).
- Снять бэкап вручную, без выкатки: `bash /opt/crm/prod/backup.sh` (на сервере).

Ежедневный бэкап запускает расписание сервера (cron пользователя `crmapp`). Строку в расписание добавляет сама выкатка прода, поэтому он начинает работать после первой выкатки прода с этой версией скриптов. Проверить, что он работает (на сервере, `ssh crm`):

- в расписании есть строка с `daily-backup.sh`: `crontab -l`;
- в `ls -lh /opt/crm/prod/backups` есть файл `_daily` за сегодня (после 03:00);
- что он писал при запуске, в том числе ошибки: `sudo journalctl -t crm-daily-backup -n 50 --no-pager`.

### Восстановить базу из бэкапа

Внимание: текущая база прода удаляется и заменяется бэкапом. Всё, что внесено после бэкапа, пропадёт (но останется в копии `_before-restore`).

1. Зайдите на сервер и выберите файл:

   ```
   ssh crm
   ls -lh /opt/crm/prod/backups
   ```

2. Запустите восстановление, указав файл:

   ```
   bash /opt/crm/prod/restore.sh /opt/crm/prod/backups/<файл>
   ```

3. Скрипт покажет, какой файл, какую базу и какую версию приложения затрагивает, и попросит ввести `yes`. Любой другой ответ - отмена, ничего не меняется.
4. После `yes` скрипт сам:
   - снимает копию текущей базы (файл `..._before-restore.dump`) и печатает её путь;
   - останавливает приложение;
   - удаляет базу, создаёт её заново и загружает в неё бэкап;
   - применяет миграции текущей версии: если бэкап снят до выкатки, структура таблиц подтягивается под работающее приложение, данные из бэкапа сохраняются;
   - запускает приложение той же версии, что работала до восстановления (версия не меняется), и проверяет `/health`.
5. В конце будет `Restored ...`. Проверьте https://app.lyna.tech: контакты из бэкапа на месте.

Восстановить бэкап с компьютера: сначала скопируйте его на сервер (`scp <файл> crm:/opt/crm/prod/backups/`), дальше по шагам выше.

### Если восстановление упало

- Скрипт пишет `Restore FAILED` и готовую команду, чтобы вернуть базу, какой она была до восстановления (`restore.sh` с файлом `_before-restore`). Приложение при этом может стоять.
- Если упал только `/health` в конце, база уже восстановлена, а приложение не отвечает: посмотрите логи (`docker logs --tail 100 prod-app-1`). Сам скрипт ничего не откатывает.
